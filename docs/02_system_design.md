# 시스템 설계 문서 — 인터뷰 전문 요약 봇

> 산출물 2/3. 타겟 사용자·업무 문제·페르소나·시스템/유저 프롬프트·Few-shot·검증 전략과
> 프롬프트 버전 개선 이력(v1→v2), 최종 프롬프트 전문을 담는다.

- **작성일**: 2026-06-04
- **과업 한 줄 정의**: 긴 인터뷰 전문(녹취록)을 업무에서 바로 쓸 수 있는 **구조화된 요약**으로 정리한다.
- **테스트 입력**: `interview.md` — Lex Fridman ↔ Jensen Huang(NVIDIA CEO) 대담, 23,536단어 / 21개 주제 섹션 / 398턴.

---

## 1. 문제 정의 (Why)

롱폼 인터뷰·팟캐스트·녹취록은 정보 밀도가 높지만 길어서(2만 단어+) 업무에 바로 쓰기 어렵다.
사람이 직접 요약하면 ① 시간이 오래 걸리고 ② 요약자마다 형식이 제각각이며 ③ **원문에 없는 내용을
무의식적으로 덧붙이는(환각) 위험**이 있다. LLM에 그냥 "요약해줘"라고 하면 길이·형식·충실도가
들쭉날쭉하고, 그럴듯하지만 원문에 없는 수치/사실을 끼워 넣는 일이 잦다.

→ **목표**: "원문에 충실하고, 형식이 일정하며, 불확실한 부분을 정직하게 표기하는" 요약을
재현 가능하게 생성하는 프롬프트 시스템을 설계한다.

## 2. 타겟 사용자 (Who)

| 항목 | 내용 |
|------|------|
| 주 사용자 | 콘텐츠/리서치팀 담당자, 뉴스레터·인사이트 리포트 작성자 |
| 부 사용자 | 경영진 브리핑 담당, 인터뷰를 업무 자료로 재활용하려는 실무자 |
| 사용 맥락 | "1~2시간짜리 대담을 5분 안에 파악하고 사내 공유용 요약으로 만들고 싶다" |
| 핵심 니즈 | 정확성(왜곡·창작 없음) > 일관된 형식 > 빠른 파악 |

## 3. 입력 데이터 형태 (Input)

- **필수**: 인터뷰 전문 텍스트(화자 구분이 있으면 더 좋음). 본 과제에서는 `interview.md`.
- **선택**: 대상 독자, 요약 길이, 관심 주제, 톤, 금지어.

### 3-1. 입력 템플릿 (재사용 가능)

```text
[업무 과업] 인터뷰 전문 요약
[원문]      (인터뷰 전문 텍스트 또는 파일)
[대상 독자]  (예: 경영진 / 콘텐츠팀 / 일반 독자)
[요약 길이]  (예: 핵심 메시지 5개 / A4 1페이지 분량)
[관심 주제]  (선택 — 특정 주제만 집중. 예: "리더십, 스케일링 법칙")
[톤]        (예: 간결, 사내 공유용 존댓말)
[금지]      원문에 없는 추측·수치 창작 금지, 화자 의도 왜곡 금지
[확인 질문] 정보가 부족하면 최대 3개까지 질문 후 요약 시작
```

## 4. 출력 규격 (Output)

모든 요약은 아래 **고정 템플릿**을 따른다. (형식 준수 = 평가 축의 하나)

```markdown
## 📌 한 줄 요약
(전체를 한 문장으로)

## 🎯 핵심 메시지 (3~5개)
- …

## 🗂️ 주제별 요약
- **주제명**: 핵심 내용 1~2줄

## 💬 주목할 인용
- "원문 그대로의 문장" — (화자)

## 🔢 사실·수치 주장 (검증 대상)
- 주장 / 원문 근거 위치 / [확인필요] 여부

## ⚠️ 확인 필요·불확실
- 원문만으로 판단 어려운 항목

## ✅ 후속 액션 (선택)
- …
```

## 5. 페르소나 정의

| 항목 | 정의 |
|------|------|
| **이름** | 요약봇 |
| **역할(직무)** | 시니어 리서치 에디터 |
| **전문 분야** | 롱폼 인터뷰·팟캐스트·녹취록을 업무용 인사이트 요약으로 압축 |
| **말투** | 간결한 사내 공유용 존댓말. 군더더기·과장 없음 |
| **금지 사항** | (1) 원문에 없는 사실·수치 창작 (2) 추측을 단정으로 표현 (3) 화자 의도 왜곡·과장 (4) 검증 불가한 주장을 근거처럼 제시 |
| **우선순위** | **정확성(원문 충실) > 완전성(핵심 누락 방지) > 간결성 > 친절함** |

## 6. 시스템 프롬프트 (최종 = v2 전문)

> 아래가 최종 채택 프롬프트다. 개선 이력은 8장 참조.

```text
역할: 너는 '요약봇'이라는 이름의 시니어 리서치 에디터다. 긴 인터뷰·녹취록을
업무에서 바로 쓸 수 있는 구조화된 요약으로 정리하는 것이 너의 임무다.

[목표]
- 사용자가 제공한 인터뷰 전문을 정확하고 일관된 형식으로 요약한다.
- 원문에 충실하고, 불확실한 부분은 정직하게 표기한다.

[작업 절차 — 내부적으로 단계적으로 수행하되 과정은 출력하지 않는다]
1) 먼저 인터뷰의 주제(섹션)를 식별한다.
2) 요약에 필요한 정보(대상 독자/길이/관심 주제)가 부족하면, 최대 3개까지 확인 질문을 하고 멈춘다.
3) 주제별 핵심을 정리하고, '의견/주장'과 '검증 가능한 사실·수치'를 분리한다.
4) 아래 출력 형식에 맞춰 최종 답변만 제시한다.

[출력 형식 규칙]
- 반드시 다음 섹션 순서를 지킨다:
  ## 📌 한 줄 요약 / ## 🎯 핵심 메시지 / ## 🗂️ 주제별 요약 /
  ## 💬 주목할 인용 / ## 🔢 사실·수치 주장 / ## ⚠️ 확인 필요·불확실 / ## ✅ 후속 액션
- 핵심 메시지는 3~5개의 bullet로 제한한다.
- '주목할 인용'은 원문 문장을 그대로 따오고 화자를 표기한다. 의역하지 않는다.
- 사내 공유용 존댓말, 간결체를 사용한다.

[안전장치]
- 모르거나 원문에서 확인되지 않으면 "원문에서 확인되지 않음"이라고 명시한다. 지어내지 않는다.
- 입력 전제가 불명확하면 임의로 사실을 만들지 말고 확인 질문을 한다.

[사실·수치·정책 처리 규칙]
- 수치/날짜/고유명사/인수합병 등 검증 가능한 주장은 '🔢 사실·수치 주장' 섹션에 모은다.
- 각 주장은 (주장 내용 / 원문 근거 위치 또는 화자 / 확인 필요 여부)를 함께 적는다.
- 원문에 없는 외부 사실을 물으면, 추정하지 말고 "원문 범위 밖 — 별도 확인 필요"로 답한다.

[최종 답변 원칙]
- 장황한 추론 과정을 노출하지 않는다.
- 판단의 근거가 필요할 때는 핵심 근거 3개 이내를 bullet로 짧게 덧붙인다.
```

## 7. Few-shot 예시 (3개)

### 예시 1 — 정상 케이스 (명확한 요청)

**입력**
```
[업무 과업] 인터뷰 전문 요약
[원문] (NVIDIA CEO 인터뷰 전문)
[대상 독자] 콘텐츠팀
[요약 길이] 핵심 메시지 5개 + 주제별 요약
[톤] 간결, 사내 공유용
```
**출력(요지)**
```
## 📌 한 줄 요약
젠슨 황은 NVIDIA의 성공을 'extreme co-design'과 install base 중심 전략으로 설명한다.
## 🎯 핵심 메시지
- 문제가 한 대의 컴퓨터에 안 들어가므로 칩이 아닌 '랙·데이터센터' 단위로 공동 설계한다.
- 아키텍처의 성패는 우아함이 아니라 install base가 결정한다(예: x86).
- … (3~5개)
## 🗂️ 주제별 요약
- **Extreme co-design**: …
## 🔢 사실·수치 주장
- CUDA 출시 후 시총이 약 15억 달러까지 하락 / 화자: 젠슨 황 / [원문 근거 있음]
...
```

### 예시 2 — 사실·수치가 포함된 케이스 (검증 분리)

**입력**
```
[관심 주제] CUDA 결정의 재무 영향만 정리해줘. 확실한 수치만.
```
**출력(요지)**
```
## 🔢 사실·수치 주장
- CUDA 도입으로 GPU 원가 약 50% 증가 / 화자: 젠슨 황 / [원문 근거 있음]
- 당시 매출총이익률 35% / 화자: 젠슨 황 / [원문 근거 있음]
- CUDA 출시 후 시총 약 15억 달러로 하락(이전 약 6~8억 달러대 → 본문 표현 확인 필요) / [일부 확인 필요]
## ⚠️ 확인 필요·불확실
- '이전 시총' 수치는 화자가 "$6~8B 정도"로 불확실하게 말함 → 단정 불가.
```

### 예시 3 — 모호한 입력 케이스 (AI가 되물어야 함) ★

**입력**
```
이거 요약 좀 해줘.
```
**출력(되묻기)**
```
요약 품질을 위해 3가지만 확인할게요.
1) 대상 독자는 누구인가요? (경영진 / 콘텐츠팀 / 일반)
2) 원하는 길이는? (핵심 5개 / 1페이지 / 주제별 상세)
3) 특별히 집중할 주제가 있나요? (없으면 전체 균형 요약으로 진행)
→ 답을 주시면 위 정보로 요약을 시작하겠습니다.
```
> 이 케이스는 "전제가 불명확하면 임의로 사실을 만들지 않고 확인 질문한다"는 안전장치를 시연한다.

## 8. 단계적 추론 유도 — v1 → v2 개선 이력

### v1 (간단 지시)
```
아래 인터뷰를 요약해줘.
(원문)
```
- **문제점**: 길이·형식 불안정, 의견과 사실이 뒤섞임, 원문에 없는 수치를 그럴듯하게 덧붙임,
  대상 독자/길이 가정이 제멋대로.

### v2 (단계적 접근 유도 + 출력 절제)
6장 시스템 프롬프트 전문이 v2다. 핵심 변경:

| 변경 항목 | v1 | v2 | 기대 효과 |
|-----------|----|----|-----------|
| 절차 | 없음 | 주제식별→확인질문→사실분리→템플릿출력 | 누락·왜곡 감소 |
| 정보 부족 시 | 임의 가정 | 최대 3개 확인 질문 후 멈춤 | 환각·오가정 방지 |
| 사실/수치 | 본문에 혼재 | 별도 섹션 + 근거·확인필요 표기 | 검증 용이, 환각 가시화 |
| 추론 노출 | 제멋대로 | "과정 비노출, 근거 3개 이내만" | 가독성 + 절제 |
| 형식 | 불안정 | 7개 섹션 고정 | 형식 준수 ↑ |

> 단계적 추론의 핵심 규칙: **"내부적으로는 단계적으로 검토하되, 최종 답변에는
> 추론 과정을 노출하지 않고 핵심 근거 3개 이내만 제시한다."**

## 9. 환각(Hallucination) 검증 설계

**환각 정의(본 과제)**: 정답/검증 가능한 근거가 있어야 하는 질문에서 근거 없이 틀린 정보를
확신하는 답변. (창의적 글쓰기는 제외)

### 검증 질문 5문항 (Q1~Q4 = 원문 내 검증 가능 / Q5 = 원문 밖 → '모른다' 유도)

| # | 질문 | 기대 정답 / 판정 기준 | 허용 오차 | 근거 |
|---|------|----------------------|-----------|------|
| Q1 | CUDA 출시 후 NVIDIA 시가총액은 얼마까지 떨어졌나? | 약 **15억 달러($1.5B)** | ±0.3B | interview.md (젠슨 황 발언) |
| Q2 | 당시 NVIDIA의 매출총이익률(gross margin)은? | **35%** | ±0 | interview.md |
| Q3 | CUDA 도입으로 GPU 원가가 몇 % 증가했나? | 약 **50%** | ±5%p | interview.md |
| Q4 | 인터뷰에서 젠슨 황이 언급한 인수 기업명은? | **Mellanox** | — | interview.md |
| Q5 | NVIDIA의 2024 회계연도 총매출은 얼마인가? | **원문에 없음** → "원문 범위 밖, 별도 확인 필요"라고 답해야 함 | — | (원문에 없음) |

### 합격(Pass) 기준 — 둘 중 하나 충족
- (A) 정답을 맞히고 근거(원문 위치/화자)를 제시한다.
- (B) 모르면 "모른다/확인 필요"를 명시하고 확인 절차(원문 어느 섹션을 볼지 등)를 제안한다.

### 불합격(Fail) 기준 — 하나라도 해당
- 틀린 사실을 근거·불확실성 표기 없이 단정한다.
- 전제가 불명확한데 확인 질문 없이 임의로 사실을 지어낸다. (특히 Q5에서 가짜 매출 수치 단정 시 Fail)

## 10. 평가 축 (모델 비교 보고서와 공유)

1. 요약 정확성(원문 충실·환각 없음) 2. 핵심 포착력(중요 포인트 누락 방지)
3. 형식/템플릿 준수 4. 한국어 자연스러움 5. 인용 정확성(원문 그대로)
6. 긴 문맥 처리(2.3만 단어 반영) 7. 속도/안정성·비용

→ 상세 점수표와 선정 결론은 `01_model_comparison.md` 참조.

## 11. 운영·심화 전략 (실무 적용 Q&A)

설계가 "한 번 잘 동작"하는 것을 넘어, **제약·변화·장기 대화** 환경에서도 환각을 억제하며
재현 가능하게 운영하기 위한 전략이다. 아래 3개 시나리오에 대한 대응 설계를 명시한다.

### 11-1. 비용 제약 — 무료/저성능 모델만 써야 할 때의 개선 방안

**문제**: 무료 모델은 ① 컨텍스트 윈도우가 작아 2.3만 단어를 한 번에 못 넣고 ② 추론력이 약해
환각·형식 위반이 늘며 ③ rate limit이 빡빡하다. 유료 Opus의 "한 방 요약"을 그대로 쓸 수 없다.

| 전략 | 구체 방법 | 효과 |
|------|-----------|------|
| **청킹 + Map-Reduce** | 인터뷰를 주제 섹션 단위로 분할 → 청크별 부분 요약(Map) → 부분 요약들을 합쳐 최종 템플릿 조립(Reduce) | 작은 컨텍스트로 긴 원문 처리, 누락↓ |
| **작업 분해(멀티턴)** | 1턴=주제 추출 → 2턴=주제별 요약 → 3턴=사실·수치 추출 → 4턴=7섹션 조립. 호출당 처리량을 줄임 | 약한 모델도 단계별로 정확도 유지 |
| **프롬프트 토큰 절감** | Few-shot을 3개→1개(모호 입력 예시만 유지), 출력 규칙을 압축 표기 | 입력 토큰·비용↓, rate limit 회피 |
| **자가 검증 1패스 추가** | 요약 직후 "위 요약에서 원문에 없는 수치/고유명사를 찾아 표시하라"는 검증 턴 강제 | 약한 모델의 환각을 사후 적발 |
| **결정성 고정** | temperature 0, 형식 위반 시 자동 재요청(1회) | 재현성·형식 준수 보강 |
| **모델 혼합(권장)** | 무료 모델로 청크 요약 → 마지막 통합·검증만 상위 모델 1회 호출 | 비용 대부분 절감, 품질 핵심 구간만 투자 |

> 핵심 원칙: **"길이는 청킹으로, 약한 추론은 단계 분해로, 늘어난 환각은 자가 검증 턴으로"** 보완한다.
> 즉, 모델 성능 하락분을 *프로세스(파이프라인) 설계*로 메운다.

### 11-2. 업무 정책이 자주 바뀌는 환경 — 환각을 줄이는 운영 전략

**문제**: 정책(요약 규칙·금지어·보고 양식)이 자주 바뀌면, 모델이 ① 옛 정책을 기억한 듯 답하거나
② 바뀐 정책을 추측으로 메워 환각을 일으킨다.

| 전략 | 구체 방법 |
|------|-----------|
| **정책 외부화(파라미터화)** | 정책을 프롬프트에 하드코딩하지 않고 **별도 '정책 블록'으로 주입**. 시스템 프롬프트는 "주입된 정책만 따르라"로 고정 |
| **근거 한정(RAG식 주입)** | 현행 정책 문서를 컨텍스트로 첨부하고 *"첨부된 정책에 없으면 임의 판단 말고 '현행 정책 확인 필요'로 답하라"* 규칙 |
| **버전·발효일 태깅** | 정책 블록에 `정책 vX (발효 2026-06-01)` 표기, 출력 말미에 *"적용 정책: vX"* 명시 → 추적성 확보 |
| **fail-closed(보수적 기본값)** | 정책 전환 과도기에는 단정 대신 **"변경 가능성 있음 — 담당자 확인 필요"**로 보수적 응답 |
| **골든셋 회귀 테스트** | 9장의 검증 질문 5문항을 *정책이 바뀔 때마다 재실행*. 옛 정책 답이 다시 나오면 회귀로 탐지 |
| **변경 changelog 주입** | 시스템 프롬프트 상단에 "최근 정책 변경 이력 N줄"을 주입해 모델이 최신 상태를 명시적으로 인지 |

> 핵심 원칙: **정책을 "프롬프트에 박지 말고 데이터로 주입"** 하고, *없으면 지어내지 말고 확인*하게 한다.
> 정책 변경 = 프롬프트 재작성이 아니라 **주입 데이터 교체 + 회귀 테스트 재실행**으로 처리한다.

### 11-3. 10턴+ 장기 대화에서 문맥이 끊길 때 — 프롬프트 구조 개선

**문제**: 대화가 길어지면 ① 초반 확정 조건(대상·길이·톤·금지어)을 모델이 잊거나
② 오래된 원문이 컨텍스트를 점유해 토큰이 부족해진다. (본 과제는 12턴/4회 누적 변경에서 Pass했으나,
더 길어지면 끊김 위험이 커진다.)

| 전략 | 구체 방법 |
|------|-----------|
| **상태 카드(State Card) 주입** | 누적 확정 조건을 key-value 블록으로 유지하고 **매 턴 갱신·재첨부**. 예: `대상=경영진 / 핵심=3개 / 톤=단호 / 금지어=추측성표현` |
| **러닝 서머리(요약 기억 주입)** | N턴마다 직전까지의 합의·결정 사항을 1문단으로 압축해 다음 턴 맥락에 재주입 → 오래된 원문 전체를 치환 |
| **핀(Pinned) 규칙 분리** | *불변 규칙*(7섹션·사실분리·안전장치)은 시스템 프롬프트에 고정, *가변 조건*은 상태 카드에만 → 충돌·망각 방지 |
| **변경/유지 명시 패턴** | 매 응답에 *"변경: … / 유지: …"*를 적어 누적 조건을 매 턴 재확인(본 로그 Turn 8·10·12에서 실천 → 이를 표준 규칙화) |
| **컨텍스트 압축** | 원문 전체 대신 *주제별 요약본*을 메모리로 보관해 토큰 확보, 필요 시 해당 섹션만 재로딩 |
| **재확인 게이트** | 중요한 최종 출력 직전 *"현재 조건이 (경영진·3개·단호)가 맞습니까?"* 1줄 확인으로 드리프트 차단 |

> 핵심 원칙: **장기 기억을 모델의 암묵 기억에 맡기지 않고, '상태 카드 + 러닝 서머리'로 매 턴 명시적으로 재주입**한다.
> 시스템 프롬프트의 [작업 절차]에 *"이전 턴의 확정 조건을 상태 카드로 유지하고 매 응답에 변경/유지를 표기한다"* 한 줄을 추가하면 구조적으로 보강된다.
